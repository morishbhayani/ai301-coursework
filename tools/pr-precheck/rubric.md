# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff matches the plan | Every file and hunk in the diff read against the plan's scope, files, and approach plus its Deviations notes; the description's claims about what changed read against the diff | Pass if every change in the diff is named by the plan or disclosed as a deviation (in the plan's notes or the description), AND everything the plan commits to delivering is in the diff or disclosed as left out, AND the description claims nothing the diff does not do. Fail if the diff adds unplanned behavior (a new option, flag, setting, rename pass, rewrite of an unrelated function or file) or drops a planned part without saying so, or if the description claims "exactly as planned", "no other changes", or a deliverable (e.g. docs updated) that the diff contradicts. An honestly disclosed shortfall or deferral passes. | required |
| Evidence proves the fix | The test evidence and the description's testing section read against the plan's test plan and the issue's repro | Pass if (1) the plan's main repro trigger (the same input/path that failed) is shown run before and after the change, with the observable outcome flipping from the failing result to the expected one; (2) every other failure mode or repro the plan's test plan names is addressed with an observed result (a one-line stated outcome for a control or secondary case is enough); and (3) the repo's own test/check command is named with its result (a stated "`go test ./...` passes" counts; pasted output is not required). Fail if the main repro has no before/after (only "tested locally", "works now", "verified on my machine"), if the evidence exercises a different or unchanged path (a control that never broke) instead of the reported trigger, if a failure mode the plan names is never mentioned, or if no repo test/check command is named at all. A check that fails or cannot run, reported honestly, does not fail this check. | required |
| Diff is clean and reviewable | The diff's hunks and the commit messages | Pass if every hunk serves the fix or its tests. Fail if the diff contains debris: debug prints or logging left in, commented-out code or earlier attempts, dead/unused functions, formatting or re-indent churn, import reshuffles, or reprinted unchanged lines unrelated to the fix. Commit-message style alone does not fail this check. | required |
| Repo standards are met | The repo-facts block's PR template and contribution/AI policy (live: `.github/PULL_REQUEST_TEMPLATE.md`, `docs/CONTRIBUTING.md`, course rules) read against the title, description, and diff. Every package is treated as AI-assisted work. | Pass if the description satisfies every requirement the repo states for a PR: required template sections or checklist items are present and filled (e.g. an issue link such as "closes #N" when asked), any file the policy requires for this kind of change (e.g. a changelog/whatsnew entry) is in the diff, and, if the policy requires AI-use disclosure, the description states the tool and extent of use. Fail if a stated required section, link, required file, or required disclosure is missing. If the repo states no template or no AI policy, its absence asks nothing. | required |
| Description explains the change | PR title and description read against the diff | Pass if the title and description say what changed and why, in terms a reviewer can check against the diff. | preferred |

## Verdict rule

`accept` only if all four `required` checks are graded `pass`. Any `required` check graded `fail` or `unclear` makes the verdict `reject`; `unclear` counts as a fail because a PR that cannot be verified from the package is not ready to submit. The `preferred` check is graded and reported but never changes the verdict. An honestly disclosed shortfall is not by itself a reason to reject.
