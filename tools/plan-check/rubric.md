# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis follows the repro evidence | The plan's stated cause (diagnosis / cause line) read against every step, control run, and artifact in the repro-evidence block (live: the student's posted repro comment as quoted in the drafts) | Pass if the stated cause explains the behavior the repro evidence shows AND is not ruled out by any control run, timing matrix, or intermediate artifact in that evidence. Fail if a control in the evidence already shows the blamed component working, or shows the failure occurring before/without the blamed component (e.g. the data is already wrong before the step the plan blames). Adopting a thread's or reporter's diagnosis does not pass on its own: the cause must still fit the evidence. A cause labeled as a hypothesis passes only if it is consistent with the evidence. | required |
| Change is one bounded fix | The plan's scope / in-scope and not-in-scope statements, its numbered changes, and the plan comment's description of what will be built, read against what the issue asks for | Pass if every change the plan commits to building is needed to fix the reported behavior (the fix itself, its regression tests, and the minimum supporting change). Explicitly deferring related work to a follow-up, or honestly scoping down to a subset of the problem with reasons, still passes. Fail if the plan commits to building work the issue did not ask for alongside the fix: migrations or dependency swaps, redesigns or rewrites of the surrounding subsystem, new options or settings, UI rework, or "while I'm in the area" fixes, even when the core fix inside it is correct. | required |
| A stranger could start building | The plan's files / areas list and its approach steps | Pass if the plan names where the change lands (specific file(s), function(s), or a named component and code path such as "the reattach path in `zellij-server`'s client connection handling") AND commits to one chosen approach for the change, so someone else could begin the edit without asking the author anything. Pinning exact function names during the build is fine when the code path and the approach are already decided. Fail if the location is "somewhere", a list of candidate layers or libraries still undecided, "profile first then decide", or if the core decision is deferred to build time ("whichever is easier"). | required |
| Test plan proves the fix observably | The plan's test plan read against the repro evidence's trigger steps and their failing artifact | Pass if the test plan re-runs the reported trigger (the repro steps, or the issue's test case turned into a regression test) and names the specific observable outcome that must change from the failing artifact to the expected one (an output, exit code, color, passing assertion, measured number). Fail if the only test is a generic suite run ("run the full test suite", "CI passes"), a feeling ("should feel fast", "nothing else should feel broken"), or anything that would pass whether or not the fix worked. | required |
| Comment engages the thread's direction | Thread highlights (live: the issue thread) for explicit direction from the owner, maintainers, members, or collaborators, read against the candidate plan and the plan comment | Pass if the thread has no explicit maintainer direction relevant to the fix, OR the plan and comment follow that direction, OR they explicitly acknowledge it and give a reason for departing from it. Explicit direction includes: a maintainer naming the culprit code location, proposing or rejecting a fix approach, posting a patch or test build and asking for testing, or pointing to an existing PR. Fail if such direction exists and the comment proposes a different direction (e.g. a workaround or docs-only change) without mentioning it. | required |
| Comment complies with the repo's stated policy | Repo-facts block's contribution policy, including any AI-use policy (live: CONTRIBUTING / AI policy files and the scope's house rules), read against the plan comment. Every package is treated as AI-assisted work. | Pass if the comment satisfies every explicit contribution requirement that applies to an issue comment. If the policy requires disclosure of all AI usage in any form, or explicitly requires disclosure in comments, the comment must state the AI tool used and the extent of help; if it does not, fail. If the policy only asks for disclosure in pull requests, asks comments to be in the contributor's own words, or states no AI policy, a comment with no disclosure passes. | required |
| Unknowns are stated, not hidden | The plan's risks / unknowns section and its causal claims, read against what the repro evidence actually establishes | Pass if the plan names what it has not verified (or nothing material is unverified) and does not present guesses as established facts. | preferred |

## Verdict rule

Accept only if every `required` check is graded `pass`. Any `required` check graded `fail` or `unclear` makes the verdict `reject`: an `unclear` counts as a fail, because a plan whose readiness cannot be verified from the package is not ready to build from. `preferred` checks are graded and reported but never change the verdict.
